## SWE 任务的构成

给一个代码仓和一个问题（issue，可以是 bug 或 feature 请求），让 AI 读懂问题、在仓库里翻找线索、最后改出 patch——这就是 SWE agent 的工作模式。

难点不在“改代码”这个动作,而在**怎么判断它是否改对了**。

里程碑性的 SWE-bench **用测试来判**：一个 bug 有无数种改法，人工评审全无可能。
这样的测试包含两部分：打 patch 前 fail、打对之后它 pass（fail-to-pass），同时不能把原本好的功能改坏（pass-to-pass）。于是任务被组织成——

```
repo + base_commit + 问题描述(issue) + gold patch + 测试(F2P/P2P) + 可执行环境
```

**"对不对"就从主观判断,变成了自动、客观、可复现的机器判定**。快、准、严,这是整个方向能规模化造数据和训练的地基。

但快准严不是没有代价的：自动判定器的判定逻辑但凡有缝，就有被 hack 的空间——模型可以不真解题却通过测试。此一节后文当有展开。

**从一条任务,到一个会解任务的系统。**
一条任务只是一份静态数据。而一个能自我改进的系统,得能把这样的任务反复地真跑起来:建一个干净环境、让 agent 动手、判定结果、再销毁——成千上万次。围着这条"环境的反复启停"(后面会看到,它是执行式系统真正的心跳),才长出下面这七个组件。按职责归三层,正好是这个系列的三篇:

```
   ┌── 数据层 (第二篇) ──┐   ┌ 系统层(一)┐   ┌──────── harness 层 (第三篇) ────────┐
   │  A 实例来源           │   │  B 执行环境 │   │ D agent scaffold   C 验证/奖励        │
   │    真实PR挖掘/合成注入 │   │    docker / │   │   动作空间         测试oracle+负控gate │
   │  E 数据生成           │   │    容器无关  │   │ F 训练             G 评测             │
   │    teacher蒸馏/exec无 │   │   (venv+chroot)│   │   SFT冷启动→RL      bench            │
   └──────────────────────┘   └────────────┘   └──────────────────────────────────────┘
                     └──────── 都围着中心那条"可验证任务"转 ────────┘
```

| 维度 | 它负责什么 | 核心权衡(=后面的坑) |
|---|---|---|
| A 实例来源 | 任务从哪来 | 真实-PR vs 合成注入;规模 ↔ 真实性 ↔ **泄露** |
| B 执行环境 | 任务怎么跑 | docker vs 容器无关;复现性 ↔ 成本/并发 |
| C 验证/奖励 | 怎么判一个 patch | 测试 oracle;reward hacking / **空补丁必须判0** / train-eval 一致 |
| D scaffold | agent 怎么交互 | 裸 bash ↔ 富工具;能力上限 ↔ **泄露攻击面** |
| E 数据生成 | 训练数据怎么造 | teacher 蒸馏;execution-free vs based;覆盖 ↔ grounding |
| F 训练 | 怎么学 | SFT 冷启动 → RL;数据**规模 ↔ 质量** |
| G 评测 | 怎么量 | SWE-bench(Verified/Pro);**框架一致性陷阱** |

**关键不在组件表，在缺口。** 把真实系统叠回这张骨架上，会发现大多数工作只在 1–2 个维度上做主要贡献，而维度**之间**的横切张力，才是真正吃工程判断、也最容易翻车的地方——本系列就活在这些缺口里:

- **真实性 ↔ 泄露**(A):合成-revert 的答案藏在 git 历史/PyPI/远端,结构性漏题;真实-PR 天然干净。→ 第二篇。
- **忠实重建 ↔ 隐式打包**(B):完整环境锁在镜像里、只发布增量安装命令,无容器重建就掉一半。→ 第一篇。
- **奖励可信 ↔ reward hacking**(C):没有负控 gate(空补丁必须判 0),RL 会奖励空动作。→ 第三篇。
- **动作空间 ↔ 泄露攻击面**(D):裸 bash 能力强但暴露 `git log`;正解是治环境、不是阉割 agent。→ 第三篇。
- **规模 ↔ 质量**(A×E):规模律说越多越好,但实测自产数据真实可用率仅 ~15%——规模的前提是干净。→ 第二篇。
- **train/eval 一致 ↔ 框架过拟合**(C×G):训评同 scaffold 会过拟合到框架,换框架就崩。→ 第三篇。

还有两件贯穿全局、却最容易被跳过的事。

一是**怎么 scale up**。实例要上量——合成注入能把规模拉到 5 万+,但后面会看到,规模的前提是干净(实测自产数据真实可用率只有 ~15%);RL 的 rollout 要并发跑成千上万个环境,这才是"容器 vs 容器无关"之争真正的战场——容器无关轻、才撑得起大规模并发。scale 从来不是"多堆机器",它和每一维的质量死死缠在一起。

二是**离真实的 coding agent 还有多远**。别忘了 SWE-bench 这类任务,本质是"有测试兜底、定位明确的单点修复";而真实开发是模糊需求、跨多文件、要做设计权衡,且大多数时候**根本没有测试当 oracle**。把 SWE-bench 刷到再高,也只是真实 coding 能力的一个窄切片。这也是为什么,这个系列的目标从来不是"训出一个 SOTA agent"(以我们的基建和投入,诚实说也训不出),而是把这条路本身、连同路上的坑讲清楚——对想走同一条路的人,一张诚实的地图,也许比一个漂亮的分数更有用。

一句话地图:**SWE-agent = 「可验证任务(C/G)」× 「实例供给(A)+ 环境(B)」× 「动作空间(D)」× 「数据(E)→ 训练(F)」;各家只占一两维,真正的判断力全在维度之间的张力里。**

而本篇(系统层),就从最先卡住我们的那道坎讲起:一个环境,怎么在没有 docker 的机器上被忠实地重建出来——以及为什么这件"听起来是运维小事"的事,掉了一半的数据。
