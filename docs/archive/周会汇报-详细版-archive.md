# SWE-agent 训练全流程：自产数据 → 冷启动 SFT → 跑通 8B，并多角度审计修复打分管线

## 1. 背景与目标

**背景**

目标是在 Ascend/aarch64 上自建并跑通 SWE-agent(仓库级代码修复 agent)的**端到端训练系统**:训练 → 推理 → 评测,配上**自产的 SFT 数据**(用 GLM-5.2 当 teacher 生成轨迹)与 **RL**,在 ≤8B 规模上验证整条链路。交付物是**训推流水线**。

**目标**
> 把 "数据生产 → SFT 冷启动 → RL → 评测" 这条链路在 8B 上端到端打通、保证每个环节**可信、可复现**。

本周重点:跑通从自产数据到 8B 冷启动模型的前半条链路,并对数据/打分的**可信度**做核查。

---

## 2. 流水线现状与可用性分析

### 2.1 一条可训练样本的构成(与 SWE-smith 实例对齐)

`repo` + `base_commit` + `需求描述` + **`测试(fail-before / pass-after)`** + `gold patch` + `可执行环境`。
其中**"测试" 是核心**:改动前自动判 "未修复"(buggy→0)、打上正确修复后判 "已修复"(gold→1)。两边都成立,才证明这个测试**真在测这个 bug**——这是数据能用于训练/RL 奖励的前提。

### 2.2 数据来源与现状

| 环节 | 现状 | 结论 |
|---|---|---|
| 实例池 | SWE-smith 本地 ~5.9 万实例(venv+conda+chroot,无 docker 镜像) | 具备 |
| 需求/轨迹 | GLM-5.2 teacher 经 mini-swe-agent scaffold 生成多轮轨迹 | 具备 |
| 可执行环境 | 容器无关的 build-at-path venv + chroot,aarch64 跑通 | 具备 |
| faithfulness 验证 | gold→1 ∧ buggy→0 双向筛 | 具备(见 2.4) |
| resolve 判定 | model-patch 打分路径 | 本周发现 bug → 已修复并验证(见第 4 节) |

### 2.3 可用性漏斗(SFT 数据)

```
GLM 生成轨迹 ~930  →  干净 SFT 430  →  (可重打分子集 402)
```

| 丢弃原因 | 数量 | 性质 |
|---|---:|---|
| **git 历史泄漏** | 269 | **SWE-smith 结构性缺陷**:repo 历史里就含答案,agent `git show` 抄到了——检出此 bug 并剔除 |
| 步数/预算耗尽 | 129 | 轨迹不完整,正常丢弃 |
| 判为未解决 | 93 | ⚠️ 用的是已知有问题的打分路径,此档不可靠 |
| 空补丁/pip泄漏/超长/仅测试 | 31 | 杂项 |

→ 含义:**有效可用规模显著小于生成总量,主因是数据结构性泄漏 + 打分可信度问题**,而非单纯生成失败。这也决定了数据侧要"先修可信度、再走量"。

### 2.4 RL 池(奖励的根基)

经本周审计修正后:`faithful_verified 954` + `deepscreen1 真buggy 562` + `deepscreen2 真buggy 498` = **候选池 2014**。
- 审计发现旧池(1620)里有 **104 个是"测试根本没跑起来"(ModuleNotFoundError)误判为 buggy→0** 混进来的——已按"≥1 个 F2P 实测 FAILED"的严格门槛剔除。
- 同时把第二批 deepscreen 的 498 个真 buggy 纳入。
- ⚠️ 后续核查:整池 gold→1 侧用的是有 bug 的旧打分器、未复检;base 954 的 buggy→0 也待用修好的打分器复检。**2014 为候选量,非已验证可用量。**

## 3. 本周成果

**(1) 端到端跑通:自产数据 → 8B 冷启动 SFT 模型** ✅
- 430 条干净轨迹(faithful + 非空补丁 + 已过 git 泄漏过滤)→ verl FSDP SFT,8×NPU,SP=8,序列长 28K,全 offload。
- 3 epoch 训练成功:**train/loss 0.69 → 0.377**,无 OOM;FSDP 分片已转成 HF safetensors(16G,可直接推理/评测)。
- 并把 "训完自动转 HF" 写进训练脚本,后续全量训完即出可用模型。

**(2) RL 奖励候选池 ~2000 + 仍在复检** ✅(详见 2.4 的可靠性说明)

**(3) RL 框架打通** ✅
基于 SkyRL(经若干 patch 实现 Ascend 支持)+ codescout 示例,奖励函数走与训练一致的 pre_check 路径。

**(4) 多角度对抗式审计 + 修复打分管线(本周关键)** ✅
核查 "lockdown 实验 100% 解出" 这个反常结果起,先用 5 组对照实验定位到 model-patch 打分路径 vacuous(空补丁也判 resolved,98.6% 虚高);**但单人救火式排查反复漏掉根因**,遂改用**多角度对抗式审计**(4 个角度并行审、每个发现派独立 skeptic 证伪)。一轮挖出 **13 个确认问题**,其中:
- **根因坐实**:打分路径根本没在评模型补丁——参数被静默丢弃,它靠 `patch` 工具的 auto-reverse 巧合每次都评成了 gold 修复(详见第 6 节)。
- **6 项问题已全部修复并验证**。判别测试:真模型补丁 resolve 从修复前 98.6% 虚高降到现实的 **82%**(5/28 被正确判为没修好),错误补丁 0 假通过。
- **价值**:多角度审计找回了线性排查反复漏掉的东西——验证了"换打法、从多角度 review"的判断。

---

## 4. 难点与风险

1. **打分管线 bug(本周核心,6 项已全部修复+验证)**:根因及其余 5 项均已修复,判别验证通过(第 6 节)。**残留**:此前的 resolve 标签是用坏 scorer 打的 → 需用修好的 scorer 重新打分/复检才可信(SFT 数据 + RL 池均在复检)。
2. **此前 "RL 池绝对安全" 的判断被审计推翻**:实有污染(测试没跑起来误判 buggy→0),且 gold→1 侧整池用旧打分器认证、未复检。教训:单点"看着对"不等于安全,需对抗式交叉验证 + 可执行验收 gate——已纳入流程。
3. **数据可用性偏低**:真正干净可用规模小,主因是 git 历史泄漏(结构性)+ 打分可信度。坚持"先修可信度、再走量"。
4. **冷启动数据规模偏小**:430 条偏少(文献常用千~万级)。当前定位为"流程验证 + RL 冷启动种子",质量靠 RL 拉。另:已训的 8B 有极少数样本(2 行)训练时 SUBMIT 动作被右截断(长度过滤 bug),不致命,重训前会修。
5. **执行/工程毛刺**:本周踩了若干环境/配置坑(venv 重定位、打分配置、模型合并节点选错等),已逐一修正并固化为检查项,但确实拖慢节奏。

---

## 5. 下一步

1. **重筛拿可信数据**:固化"空补丁负控必须判 0"自检 gate → 用修好的 scorer 重打 430 SFT + RL 池 gold→1/buggy→0 复检 → 得到**真实**可用规模(全量重打分本身即最终体检)。
2. **数据走量(重筛之后)**:再扩量(更多 faithfulness 筛查 + 受控 GLM 生成,严格记账控成本)。
3. **RL 跑通**:用复检后的干净池 + 8B 冷启动种子,把 RL 训练在 Ascend 上端到端跑起来。
4. **闭合评测**:8B 冷启动/RL 后模型在 chroot 评测体系上测分,闭合 训练→推理→评测。

## 6. 重要 bug 与修复方法(本周审计)

| Bug | 症状 | 根因 | 修复 | 状态 |
|---|---|---|---|---|
| **打分路径 vacuous(根因)** | 没做修复的空补丁也判 "已解决",resolve 标签全失真 | `model_patch_file` 参数只在 SWEBench 数据源接了,swesmith 数据源**静默丢弃** → 评分用的还是原始 bug diff,被 `patch --fuzz` 的 auto-reverse 巧合"反成"了 gold 修复 → 永远通过 | 给 swesmith 数据源接上 `model_patch_file`,正确用模型补丁评分 | ✅ 修复+验证(空补丁→0) |
| **测试名子串假通过** | 没收集到的目标测试,会"蹭"同名兄弟(如 `test_exc_info` 蹭 `test_exc_info_renamed`)的通过状态 | 用了 Python **子串**匹配 `name in key` | 改**锚定匹配**(精确 / 参数化 `name[...]` / 类名前缀 `.name`),拒绝中段子串 | ✅ 修复+验证(单元+gold/buggy 回归) |
| **buggy 门槛混淆** | 工具链报错(ModuleNotFound,测试根本没跑)也被当作 "buggy→0" 通过 → 污染 RL 池 | 门槛只看 `reward==0`,而 0 混了真失败/超时/没跑起来 | 改为"**≥1 个 F2P 实测 FAILED**"才算;池内 104 个污染已剔除 | ✅ 数据级清理 |
| **死代码容差** | p2p/f2p 容差参数实际失效(且若误启用会放松评分) | `return` 之后跟了一行不可达代码 | 删除死行 + 注明 swesmith 为严格全过 | ✅ 修复 |
| **长度过滤截断 submit** | 个别训练样本结尾的 SUBMIT 动作被右截断 | 过滤用 `字符数/4` 估 token,低估 ~7.6%,松于训练的真 token 上限 | 改用**真 tokenizer**(apply_chat_template)估算 + 留余量 | ✅ 修复 |
| **git 泄漏检测可绕过** | `git checkout HEAD~2`/`cat-file`/`log -p` 等取到干净源码却漏检 | 检测是按**命令字面**白名单,非按"读历史源码"的能力 | 改**能力检测**(verb 集 + 历史 ref),单元测试 6 绕过抓住、7 benign 不误伤 | ✅ 修复 |

**修复后判别验证**:空补丁→0 / gold→1 / buggy→0 / 错误补丁→0 个假通过 / 真模型补丁→23/28=82%(对比修复前 98.6% 全过)。并把"空补丁负控必须判 0"固化为打分脚本自检 gate,防回归。

> 方法论收获:**对抗式多角度审计**(并行多视角 + 每个发现独立证伪)找回了线性救火反复漏掉的根因与并发问题;打分/奖励这类"静默错"必须靠"空补丁负控必须判 0"这类**可执行验收 gate** 兜底,不能靠肉眼读代码。

> 本周把前半条链路(数据 → SFT → 8B)端到端打通,并通过多角度审计**定位+修复**了打分管线的根因 bug;下一步以 "修完 → 重筛/复检拿可信数据 → 走量 → 上 RL" 的顺序推进,不在不确定性上提前重押。
